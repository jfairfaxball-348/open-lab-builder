## Purpose

This is an engineering check. Can an unattended hosted one-hour run on
`gpt-5.6-luna` survive a registered Laboratory-side runtime crash and recover
correctly? "Correctly" means:

- the same run id;
- a conserved active-time budget, step budget and request ceiling;
- one provider-reported model version, pinned under ADR-0021;
- no unrecorded coaching;
- an intact archive.

Behaviour is reported separately and is **not** a pass criterion. Idle time is
neither a failure nor a success. Uptime is not autonomy.

- `reliability_fault`: `runtime-kill-at-active-second-v1`. When the run's active
  time reaches the registered second, the supervisor records a
  `reliability_fault` action and kills the runtime process tree. It happens once,
  regardless of model state. The kill times differ across runs so that the fault
  can land in an active phase as well as an idle one. Which phase each kill hits
  is observed, not assumed.

Recovery restores the last complete-step checkpoint, which may be up to about
60 s earlier. Model steps after that checkpoint are replayed. Replayed requests
are new provider requests: they count against the ceiling, and the model may
answer differently. Every replay is recorded and reported, never hidden.

**Broker** (subject to owner approval): `min_interval_s` 20, `per_run` 180
(across all segments of a run), `max_attempts_per_step` 2,
`per_day`/`total` 1570 (ledger 1030 + 3 × 180). Same cadence as S011p.

## Procedure and stop rule

1. Runs go in order 1, 2, 3, one at a time. The operator launches each with
   `uv run ols run experiments/s011a/hour-N.json` only after verifying the
   previous one.
2. After each run, the operator runs `ols verify` and classifies the run (below)
   **before** launching the next.
3. **Stop rule.** Launch nothing further after any of these:
   - a provider terminal outcome (usage limit, identity change, access loss);
   - a run that is not `clean`;
   - a host interruption (sleep, reboot).

   No replacement or repeat is allowed under this registration. A host
   interruption may be resumed only by the run's own registered startup
   recovery. That recovery is limited to the same restart budget, so a second
   restart exhausts it.
4. No human messages to the model, and no changes to settings or the broker
   profile between runs. Doing either would change the treatment, so the next
   resume is refused.

## Per-run classification (engineering)

**clean** requires all of the following:

- exactly one `reliability_fault` action and one `recovery_restart`;
- the run ends by its 3600 s deadline (`terminated`/deadline) or `max_steps`;
- requests stay within 180;
- every accepted response reports the same `model_version`, and resumed
  segments record `hosted_identity_pin`;
- the frozen configuration and policy are unchanged;
- `ols verify` reports the archive intact.

Any other outcome is one of:

- **failed-recovery**: the restart was refused or the restart budget was
  exhausted;
- **censored-provider**;
- **interrupted**;
- **invalid**.

Exit for S011a: **three consecutive clean runs**. Anything less leaves S011a
incomplete, and the result is reported as observed.

## Reported per run (behaviour separately)

The engineering report covers:

- the fault time and which phase it hit (active or idle);
- the checkpoint restored and the steps replayed;
- recovery latency;
- requests, including replays and retries;
- tokens;
- model versions;
- the idle onset;
- the end reason.

The behaviour panel covers the capabilities used, memory writes and reads,
continuations delivered, and statements recorded as agent claims. It is
descriptive and n = 3. It is not an autonomy GO.
